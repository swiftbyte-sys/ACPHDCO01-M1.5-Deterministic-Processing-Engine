# M4.5 Technical Summary and Reflection

## Technical summary

The M4.5 branch extends the existing deterministic evidence-processing engine with structured telemetry and a paced concurrent benchmark. The engine stores evidence operations in an append-only JSONL write-ahead log (WAL), serializes mutations using a process-local reentrant lock, fsyncs accepted events before publishing them in memory, and uses stable event IDs for idempotency.

The new telemetry component emits one JSON record per completed operation. Each record contains an ISO-8601 UTC timestamp, trace ID, operation name, end-to-end latency in microseconds, and status code. Error records include the exception type without copying potentially sensitive exception messages.

The benchmark offers a configurable number of synthetic evidence-ingestion operations at a paced target rate. It supports concurrent workers, seeded application-level request drops, bounded randomized retry delays, and a stable event ID across retries. Its report distinguishes offered, delivered, committed, and failed operations and calculates P50, P90, P99, and P99.9 latency. It also reopens the WAL after the workload and compares the recovered state with the live state before reporting an integrity PASS.

## Design decisions

1. **Durability before publication:** A successful mutation is appended to the WAL and fsynced before its in-memory state is updated. This makes the commit boundary explicit.
2. **Process-local serialization:** A reentrant lock prevents concurrent threads in this process from interleaving state mutations. It is not a distributed lock and does not coordinate multiple processes or hosts.
3. **Idempotent retries:** A stable event ID prevents the same accepted operation from being applied twice when a client retries.
4. **Bounded retries:** Retry attempts and delays are finite to avoid unbounded retry amplification.
5. **Observable outcomes:** The benchmark reports measured results rather than treating the configured 10,000 offered operations/second as achieved throughput.

## Failure model and limitations

The 30% injector simulates application-level request loss before the receiver processes an operation. It does not drop physical network packets. A PASS means that, for the configured synthetic workload and the tested runtime/storage environment, all offered operations were committed, no request exhausted its retry budget, and WAL replay reconstructed the same state. It is not a guarantee against arbitrary filesystem corruption, hardware failure, process termination at every possible instruction boundary, or multi-host failures.

The implementation is a single-process educational prototype. It does not implement consensus, multi-host replication, or a production-grade distributed queue. The existing qualitative engine provides an auditable evidence/coding data model; this M4.5 specification itself does not define PRISMA screening fields, effect-size estimators, meta-analysis pooling, or bibliometric measures. Those research-method features should not be claimed as implemented.

## Reflection

The main engineering trade-off is between durability and throughput. Synchronous WAL fsync provides a clear durability boundary but adds latency and serializes commits. Increasing worker count does not necessarily increase committed throughput when the WAL is the bottleneck. The benchmark therefore records actual throughput and latency percentiles, including worker-queue and retry delay, so capacity decisions can be based on measurements.

A second lesson is that failure injection must match the claim being made. Simulated application-level drops are useful for testing retry logic and idempotency, but they are not equivalent to network-layer packet loss. The failure model is stated explicitly to keep the conclusions reproducible and academically defensible.

## Reproduction

```bash
python -m pip install -e .
python -m pip install -r requirements-m2.5.txt
python -m pip install -r requirements-m3.5.txt
python -m pip install pytest-cov
pytest -q --cov=acp_engine --cov-report=term-missing --cov-report=xml
python benchmarks/run_m4_5_benchmark.py --ops 10000 --target-rate 10000 --workers 32 --drop-rate 0.30 --output m4.5-benchmark.json --telemetry m4.5-telemetry.jsonl
docker build -f Dockerfile.m4.5 -t acp-m4-5 .
docker run --rm -v "$PWD/artifacts:/data" acp-m4-5
```
